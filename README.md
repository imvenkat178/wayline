# Wayline AI

Transportation planning, journey monitoring, and a grounded travel assistant, built with React, TypeScript, Vite, and Node.js/SQLite.

**Work-in-progress checkpoint — 8 September 2026, with a Stage A stabilization pass, a durable-jobs/web-push pass, an account-security pass (TOTP MFA, session/device management, password recovery), a privacy-retention-propagation pass, a sandbox commerce-scaffolding pass, a ticket-wallet real-import pass, a multilingual-infrastructure pass, an operator-dashboard/data-quality pass, an accessibility-hardening pass, a CI/dev-workflow pass, and a catalog-knowledge-graph pass applied 9 September 2026.** This is the implementation so far, not a finished production release. All 105 requested features are accounted for in [FEATURE_STATUS.md](docs/FEATURE_STATUS.md). Sample routes, prices, crowding, reliability, and connection probabilities are illustrative, not verified schedules, quotes, or predictions.

The 9 September stabilization pass addressed every row in the roadmap's "Immediate code work before expanding scope" table: account-switch state leaks, hash routing consistency, an offline app-shell service worker, bundled OCR assets, local-timezone night-walking scoring, tracking-agency/provider separation, freshness recomputed per response instead of cached, Guardian's account scan no longer capped at 1,000, recovery alternatives checked against where the traveler can actually reach, recovery cost calculated incrementally instead of by whole-itinerary subtraction, honest per-capability integration-status reporting, and paginated MBTA feed fetches.

A follow-on pass the same day went further than stabilization: Guardian's periodic sweep is now a durable, leased, SQLite-backed job (`server/jobs.mjs`) that survives a process restart and backs off on repeated failure, instead of a bare `setInterval`; and push notifications (roadmap feature 89) are now genuinely implemented with real Web Push (RFC 8030/8291) -- a self-issued VAPID identity, a subscribe/unsubscribe control in Profile using the actual `PushManager` API, and delivery routed through that same durable job queue with per-subscription cleanup when a push service reports a subscription gone. Push defaults to a generic, non-identifying notification body; a `pushDetails` preference opts into the real alert text. All of this is code-level and unit/integration-tested; none of it has been exercised against a real browser, a live push service, a live MBTA/OTP/GBFS feed, or real user accounts at scale -- see "Known gaps and remaining work" below for what that leaves outstanding.

A further pass the same day hardened accounts (roadmap feature 95): TOTP-based multi-factor authentication (`server/totp.mjs`, RFC 6238, verified against the RFC's own Appendix B test vectors, with 8 one-time base32 recovery codes issued on enrollment), a session/device list with per-session and "sign out everywhere else" revocation (`server/store.mjs`'s widened `sessions` table, migrated in place for a pre-existing database), and a password-recovery token flow whose response is identical whether or not the given email has an account, so it can't be used to enumerate registered addresses. None of this depends on an external account: TOTP and recovery codes are generated and verified locally, exactly like any other authenticator app. Actually delivering a recovery email does need a real provider (SES, Postmark, Resend, an SMTP relay), which this environment doesn't have -- so email sending is a pluggable interface (`server/email.mjs`) with a default that logs the message instead of sending it, clearly labeled as such in the API response and here. A login against an MFA-enabled account gets a short-lived, single-use challenge token instead of a session; a wrong code does not consume that token, so a mistyped code doesn't force starting over.

A final pass the same day closed a gap this document already flagged (roadmap feature 97, "Privacy mode"): account and history deletion previously reached only the `records` table and whatever else already had a foreign key to `users` -- one piece of derived, per-user data, the durable job queue's queued-but-not-yet-delivered push notifications, could linger for up to 14 days after an account was deleted, self-healing silently rather than erroring, but still present in the database until an unrelated age-based sweep happened to run. The `jobs` table now has a real `user_id` foreign key with `ON DELETE CASCADE` (backfilled for existing rows whose referenced user still exists), so deleting an account removes its queued jobs in the same transaction as everything else; deleting just a user's history additionally retracts any still-pending push job for an alert that history deletion just removed, rather than waiting for it to no-op at delivery time. The "export everything about me" endpoint was also missing three tables' worth of account state -- it now includes active sessions, MFA enrollment status, and outstanding share links alongside records and audit history, none of which expose a raw credential (sessions and shares carry only a hashed token id, already how the UI lists them; MFA status is just the enrolled boolean).

A last pass the same day laid groundwork for real ticketing and payment (roadmap features 34, 39-41), all of which the roadmap's own triage already flagged as blocked on a signed carrier reseller/API agreement and a payment processor merchant account -- neither of which exists here, and no amount of code substitutes for either. What is now real: an order/quote/hold/confirm/exchange/reconcile state machine (`server/domain/commerce.mjs`) mirroring the same pure, event-appending pattern journeys already use; idempotent order creation using the exact same key/request-hash pattern as saving a journey; and a signed-webhook callback (`POST /api/commerce/webhook`, HMAC-SHA256 over the raw body, verified with `crypto.timingSafeEqual`) that reconciles an order without any user session, the way a real payment provider's callback would. All of it runs against a sandbox adapter (`server/adapters/payments.mjs`) that authorizes, captures and refunds only synthetic amounts and never talks to a real network -- a new Wallet tab ("Sandbox checkout") makes this visible end to end, clearly labeled, so a real provider is one adapter implementation away, not a redesign.

A closing pass the same day gave the Ticket wallet (roadmap feature 18, extending 19) a real import path instead of manual entry only: adding a ticket can now attach a photo, which is decoded for a QR/PDF417/Aztec/Code128/Data Matrix barcode entirely in the browser (`src/barcode.ts`, `@zxing/browser` -- an open-standard decoder, no issuer account or network call involved) before the photo and any decoded barcode text/format are saved with the ticket. Nothing is validated against an issuer or carrier system -- every such ticket is labeled `UNVERIFIED` in the wallet, exactly like the roadmap's own framing of this as an import, not issuance. The attached-document field has its own size cap (`server/records.mjs`'s `validateTicketDocument`, 7 MB of base64) below the request body's own raised cap for this one endpoint (8 MB, versus the shared 1 MB default everywhere else), and decoding runs from a dynamically imported chunk so the barcode library never bloats the main Wallet page load. Fixing this also surfaced and closed a real resource-leak bug in `server/server.mjs`: rejecting an oversized request body used to abandon the request stream without ever telling the client (or the socket) the connection should close, which could leave it lingering instead of closing cleanly; the 413 response now asks for the connection to close and the socket is only torn down once that response has actually been sent.

A final pass the same day built real multilingual infrastructure (roadmap features 93-94): a keyed i18n resource catalog (`src/i18n.ts`) with locale-aware date, number and currency formatting (`Intl.DateTimeFormat`/`Intl.NumberFormat` bound to the signed-in user's `preferences.language` via `src/useT.ts`), replacing the previous approach of one hardcoded positional array of nav labels and four untranslated-elsewhere phrasebook phrases. Navigation, the app shell (footer, the glance/"Watch" view), the phrasebook, and the entire Planner page -- the single page a first-time visitor is most likely to use, per the roadmap's own "Wayline simply says: Take this" framing of feature 94 -- are now genuinely localized into Spanish. The phrasebook itself was reorganized into the four categories feature 93 names by name (transit alerts, station instructions, ticketing, boarding directions), with 12 phrases total across English/Spanish/Hindi, each with a spoken-aloud (Web Speech API) button. Every non-English string here was translated by this assistant, not a certified translation service or a native-speaker reviewer -- labeled as such directly in the UI (Profile's language selector, and a note in the phrasebook itself), matching the roadmap's own acknowledgment that translation quality review is a human task no amount of code can certify. Hindi still covers only navigation and the phrasebook (unchanged from before this pass); every other page (Wallet, Journey, Profile, Trips, Commute, Inbox, Lab, Offline, Agent) remains English-only -- see "Known gaps" below for the honest scope of what "multilingual support" means in this checkpoint.

A last pass the same day hardened the operator dashboard and data-quality report lifecycle (roadmap features 98-99, hardens 100-101). `/api/operator` used to return one global `COUNT(*)` against a single hardcoded threshold -- "the current endpoint is count-only," in the roadmap's own words -- and now returns a genuine per-type breakdown (`server/store.mjs`'s `operatorReportBreakdown`): each report type is only disclosed once real distinct-contributor threshold is met (`MIN_REPORT_COHORT`, shared with `/api/community` instead of two separately hardcoded copies), and everything below that is named without a count so a rarely reported issue at a low-ridership stop can't be used to infer who filed it. A new `/api/operator/reports` worklist and `PATCH /api/operator/reports/:id` endpoint give an operator an actual moderation queue for individual reports -- deliberately not threshold-gated, since resolving "the elevator here is broken" is an operational ticket, not a demographic signal, and the reporter's identity is never included in what an operator sees. Every report also now carries a real status lifecycle (open/reviewing/resolved/dismissed) and a `resolutionNote`, visible back to the reporter through their own report list (new: a "Your recent reports" section in the report modal) rather than being write-only as before. `confidence`, previously always `null`, is now a genuine count of distinct other accounts that reported the same station and type recently (`store.reportConfirmations`) -- real confidence weighting, per roadmap feature 99's own wording, computed at write time and never retroactively inferred.

A closing pass the same day made a start on accessibility (WCAG 2.2 AA target; this does not map to one specific numbered roadmap row -- the closest, feature 25, is about accessible _routing_ filters, a different meaning of the word from the app's own keyboard/screen-reader accessibility, which is what this pass addresses). A short manual and code-reading review found and fixed two real, concrete bugs: the account switcher in the top navigation (`.profile-nav`) was a `<div>` with a click handler, unreachable by keyboard, and is now a real `<button>`; and two text inputs (the search field and the assistant's message box) had their focus outline removed with no visible replacement, now restored with a themed focus ring. Icon-only buttons were checked and already had real accessible names via `title`/`aria-label`, and the existing `Modal` component already uses the native `<dialog>` element's `showModal()`, which gives focus-trapping and Escape-to-close for free -- neither needed a fix. Automated regression coverage for this now exists (`tests/accessibility.test.mjs`, 11 tests): it compiles the actual shared UI component source (`src/components/ui.tsx`, not a hand-copied reimplementation) with esbuild, renders real instances with `react-dom/server`, and runs `axe-core` against the result in a `jsdom` document, scoped to the WCAG 2A/2AA rule set. This is honestly partial in two ways this document should say plainly: `jsdom` has no layout engine, so layout-dependent rules -- color-contrast chief among them -- are not meaningfully checked by it (a real-browser Playwright+axe run was attempted for this and is currently infeasible here: `npx playwright install` fails with a 403 from this environment's network egress allowlist trying to download the Chromium binary); and coverage is limited to the shared primitives exercised in that test file, not every page or every composed screen. No full human or screen-reader (NVDA/JAWS/VoiceOver) certification has been performed -- see "Known gaps" below.

A final pass the same day added the CI and dev-workflow scaffolding the roadmap's Maintainability section asks for: a GitHub Actions workflow (`.github/workflows/ci.yml`) that installs from the lockfile (`npm ci`) and runs typecheck, lint, test, and build on every push/PR, exactly the sequence this checkpoint's own discipline already required by hand before every commit; an ESLint flat config (`eslint.config.js`) added retroactively to an already-large codebase, which is why it enables only the rules that could be brought to a clean (0-error) state without a separate refactor pass -- see [docs/adr/0006-eslint-scope-and-ts7-compat.md](docs/adr/0006-eslint-scope-and-ts7-compat.md) for exactly which rules were left off and why, including a real, tracked upstream incompatibility between `typescript-eslint` and TypeScript 7 that this pass resolved by pinning `typescript` back to the latest 6.x release rather than building an unreproducible workaround; an MIT [LICENSE](LICENSE) file (this repository's first -- no license existed before this pass); and six architectural decision records under [docs/adr/](docs/adr/) documenting the non-obvious choices already made in code across this checkpoint (SQLite/single-process, the generic `records` table, sandbox adapters, the i18n catalog, and aggregation-threshold privacy), written after the fact rather than as a design process happening here.

A closing pass the same day started roadmap feature 44 ("Transport Knowledge Graph"), after catching a real scoping mismatch in this session's own plan: the plan had described Phase 11 as splitting the generic `records` table's journey/commute/pass usage into dedicated indexed tables, but feature 44 actually asks for real relationships among _catalog_ data (agencies, routes, stations), not a change to how a user's own encrypted records are stored -- and the records-table version would have forced a real privacy tradeoff (indexing an encrypted field means storing it in plaintext) that the roadmap item never asked for. See [docs/adr/0007-catalog-knowledge-graph.md](docs/adr/0007-catalog-knowledge-graph.md) for the full reasoning. What shipped instead: `server/catalog.mjs`'s sample corridors now carry real `agencyIds` edges to specific agencies (resolved by name, not hardcoded ids) instead of no relationship at all; `agenciesForCorridor()`/`operatorForCorridor()` are real graph-traversal functions (the latter returns `null`, never a guess, when the graph has no answer); stations are now their own entities linked to a city id and the agencies serving it, instead of a single string field; `discoverAgencies()` prefers real corridor edges when one exists and only falls back to the original name-substring match for the ~44 states with no sample corridor; and a real gap closed along the way -- "Washington State Ferries" was referenced by name in `operatorLinks` and hardcoded directly in the sample journey search, but never actually existed as a seeded agency until now. `sampleSearch()`'s sample journeys for San Francisco-Oakland, Seattle-Bainbridge and Los Angeles-LAX now name a real, corridor-appropriate operator (BART, Washington State Ferries, LA Metro) instead of a generic Amtrak/Greyhound/FlixBus guess; the three long-distance corridors (Los Angeles-San Jose, Boston-New York, Indianapolis-Chicago) are unaffected. This is real relationship data over static, non-personal reference information only -- no encryption, schema, or per-user storage changed, and the graph only covers the six sample corridors and the dozen agencies named above, not the roadmap's full route/stop/platform entity list.

## Quick start

Requires **Node.js 24 or newer** and npm. Python 3 is needed only for ZIP packaging. From this directory:

```sh
npm ci
npm run build
npm start
```

Open `http://127.0.0.1:4173`. A guest session is created automatically; registration is available in Profile. No default credentials or provider tickets are included. The included `standalone/` is a compiled checkpoint; rebuild after frontend changes. `start.sh` and `start.bat` also start the server. Opening the HTML file directly will not provide the required API.

### Development

Vite proxies `/api` to port 4174. Run in separate terminals:

```sh
# Terminal 1, POSIX shell
PORT=4174 npm start
# Terminal 2
npm run dev
```

On PowerShell use `$env:PORT="4174"; npm start` in terminal 1. Open the URL printed by Vite. `npm run preview` alone does not provide the API; use `npm start` to inspect the complete built app.

This exact two-terminal setup used to fail every mutating request (login, journey search, the Agent chat, everything except plain `GET`s) with 403 `"Origin is not allowed."`, because the browser's real `Origin` header (Vite's port) never matched the API server's own computed origin (its own port) -- a real bug, not a client misconfiguration, found by actually running the documented workflow above rather than assuming it worked. `server.mjs` now allows exactly one additional origin in non-production mode, defaulting to `http://127.0.0.1:5173` and overridable via `DEV_CLIENT_ORIGIN` if Vite runs on a different port; production is unaffected; see `tests/origin-check.test.mjs`.

## Security and privacy

Implemented controls include scrypt password hashing, hashed session/share tokens, AES-256-GCM record encryption, owner-scoped access, CSRF checks, request limits, validation, optimistic concurrency and expiring shares. Registration always grants the traveler role. Operator provisioning is unfinished; an unverified email never grants elevated access.

Implemented account-security controls also include TOTP multi-factor authentication with one-time recovery codes, a per-session device list with individual and bulk revocation, and password-recovery tokens (single-use, short-lived, and enumeration-resistant -- the API response doesn't reveal whether a given email has an account). Recovery email delivery is log-only until a real provider is configured (see `server/email.mjs`).

Development generates a local encryption key in `data/`. Securely back up the database and key; losing the key prevents decryption. SQLite metadata is not whole-disk encrypted. Key rotation, restore testing, SSO, email verification, a real email provider, proxy-aware abuse controls and formal security review remain release work. This checkpoint is not approved for production passenger data.

Offline passphrases remain in the browser. Share links are bearer credentials. Contacts do not trigger SMS, email or emergency messages. Browser speech recognition may use browser-vendor services.

## Known gaps and remaining work

1. Validate routing/provider feeds against real, live traffic. This environment has no network path to MBTA/OTP/GBFS, so vehicle-to-journey matching (now keyed on canonical agency rather than routing provider) and MBTA's now-paginated vehicle/alert fetches (with an explicit `coverageLimited` flag instead of a silent one-page truncation) are unit-tested against mocked responses only, not exercised against a live feed. Fares, platforms and accessibility evidence remain unverified.
2. The offline app shell now has a service worker (`public/sw.js`) that caches the static shell and lets the SPA boot without a connection; it has not been tested with real browser interaction (install/activate lifecycle across browsers, storage limits, multi-tab behavior). Local encrypted IndexedDB packs are unaffected by this and were already present.
3. OCR assets are bundled under `/ocr/` (tesseract.js worker plus standard and SIMD WASM cores, with their licenses), and scan cancellation is reliable across unmount/navigation. First-use and failure-path behavior have not been tested in a real browser.
4. Account switching now clears user-scoped app state and in-flight requests on identity change; hash routing is consistent for the logo, offline view, and unknown routes; night-walking scoring uses each journey's own timezone instead of `getUTCHours`. Full localization remains outstanding (see item 16); a first accessibility pass has now been made (see item 18), but it is not a full screen-reader/keyboard certification.
5. Integrate authorized ticketing, seats, payments, holds, rebooking, claim submission and refunds.
6. Add observed reliability data and calibrated prediction models; current probabilities and sample crowding are heuristics.
7. Integration-capability reporting distinguishes features that need a commercial/contracted provider ("provider required": checkout, ticketing, seat inventory, payment tokenization, rebooking, refunds, flight inventory, SMS/email) from features with no implementation in this codebase ("unsupported": native watch clients, indoor maps/AR, EV live availability) from features that are now genuinely implemented and locally configured ("configured, not checked": remote push -- see item 11 below). Eleven of the twelve remain not built; actual family tracking is separately still deferred.
8. Guardian's periodic sweep paginates through every account with a journey, commute, or pass on file instead of capping at the first 1,000 accounts, and now runs as a durable, leased, SQLite-backed job (`server/jobs.mjs`) that survives a process restart and backs off on repeated failure, instead of a bare `setInterval`. It remains single-process, not distributed across multiple workers sharing one database -- multi-worker coordination is later-stage architectural work per the roadmap's "Durable background processing" guidance, and would need a different database engine than a single SQLite file.
9. Prepared trip recovery now checks that an alternative actually departs from a stop and time the traveler could reach (not just that it shares the destination and arrives in the future), and calculates an incremental cost — netting out legs retained from the original itinerary and using a self-reported paid ticket amount when one is on file — instead of subtracting two whole-itinerary estimates. There is still no provider transaction, no real exchange/refund-rule data, and no nonrefundable-amount data anywhere in this codebase; both remain draft-only, for-review calculations.
10. Add broader integration, end-to-end, migration, load, recovery and security checks. Browser interaction testing has not been performed for this checkpoint.
11. Web push (roadmap feature 89) is now genuinely implemented -- a self-issued VAPID identity, a subscribe/unsubscribe control in Profile using the real `PushManager` API, and delivery through the durable job queue with per-subscription cleanup on a 404/410 "gone" response -- but has only been unit/integration-tested against a mocked push service (`web-push`'s `sendNotification` mocked in `tests/push.test.mjs`). It has not been exercised end-to-end against a live browser and a real push service (Chrome/Firefox/etc.'s actual push infrastructure), and the service worker's `push`/`notificationclick` handlers (`public/sw.js`) have not been tested in a real browser either.
12. TOTP MFA, session/device revocation and password-recovery tokens (roadmap feature 95) are code-level tested, including the TOTP math against RFC 6238's own Appendix B vectors, but have not been exercised against a real authenticator app or a real email provider. Password-recovery email is log-only (`server/email.mjs`'s `LogEmailProvider`) until a real provider account is configured -- the reset link is written to the server log, not actually delivered.

13. Account/history deletion now propagates to the durable job queue (a real foreign key, not just primary records) and data export now covers sessions, MFA status and shares -- but a job already orphaned by an account deleted before this pass shipped has no way to recover whose it was, and is left to the existing 14-day age-based `cleanup()` sweep, same as before. This pass is code-level tested only (`tests/privacy-retention.test.mjs`); it has not been exercised against a production-scale database or a real deletion request under load.

14. Sandbox commerce scaffolding (roadmap features 34, 39-41 groundwork) is code-level tested only (`tests/commerce.test.mjs`, real HTTP including the signed-webhook path) -- it has never been exercised against a real payment processor or carrier, because none is integrated; the adapter behind it (`server/adapters/payments.mjs`) is entirely synthetic by design. Seat inventory (row 39) is unaffected -- the state machine does not model or reserve seats at all.

15. Ticket-photo barcode import (roadmap feature 18) decodes only open barcode standards client-side (`src/barcode.ts`) and has been exercised over real HTTP with generated (not photographed) test images and synthetic barcode text (`tests/ticket-import.test.mjs`) -- it has not been tested against a real camera photo, real-world lighting/glare/skew, or an actual issuer's ticket format, and every such import is stored and displayed as `UNVERIFIED`, never checked against a carrier or issuer system.

16. Multilingual support (roadmap features 93-94) is a real i18n engine, unit-tested (`tests/i18n.test.mjs`, 11 tests covering lookup, fallback, placeholder substitution, and locale-aware `Intl` formatting), but its actual UI coverage is partial and this document says so plainly: Spanish covers navigation, the app shell, the phrasebook and the Planner page only; Hindi covers only navigation and the phrasebook; Wallet, Journey, Profile (besides its language selector), Trips, Commute, Inbox, Lab, Offline and Agent remain English-only regardless of the selected language. Every non-English string was translated by this assistant and has not been reviewed by a native speaker or a professional translation service -- exactly the "translation quality review is a human task" caveat the roadmap itself raises for feature 93, and it is surfaced directly in the language picker and phrasebook, not just in this document.

17. The operator dashboard and report moderation (roadmap features 98-99, hardens 100-101) are code-level tested over real HTTP (`tests/reports.test.mjs`, 11 tests covering the per-type cohort threshold, the moderation worklist, status transitions, reporter-visible resolution, and confidence weighting) but there is still no real path to actually become an "operator" -- registration always assigns "traveler," and the tests promote a user by writing directly to the store, exactly as FEATURE_STATUS.md's row 98 says. There is no delivery pipeline to an actual transit agency, no demand/missed-connection/transfer-failure aggregation (the roadmap's other operator-dashboard asks), and no trust/reputation system distinguishing a reliable reporter from a new one -- confidence weighting here means "how many distinct other accounts reported the same thing recently," not a calibrated trust score.

18. A first accessibility pass (WCAG 2.2 AA target) fixed two real, concrete bugs -- a keyboard-unreachable account-switcher control, and two inputs whose focus outline was removed with no visible replacement -- and confirmed icon-only buttons already have real accessible names and the `Modal` component already gets focus-trapping/Escape-to-close for free from the native `<dialog>` element. Automated coverage now exists (`tests/accessibility.test.mjs`, 11 tests, real component source compiled with esbuild and checked with `axe-core` in `jsdom`), but this is not a substitute for a full audit: `jsdom` cannot meaningfully check layout-dependent rules like color-contrast (a real-browser Playwright+axe run was attempted and is currently blocked by this environment's network egress allowlist refusing the Chromium binary download), coverage is limited to the shared UI primitives actually exercised in that test file rather than every page, and no human or screen-reader (NVDA/JAWS/VoiceOver) review has been performed.

19. ESLint (`eslint.config.js`) is now wired into CI and passes with 0 errors, but its scope was deliberately kept to what was already true of the codebase rather than a from-scratch style rewrite: `eslint-plugin-react-hooks`'s newer "React Compiler" rules (purity, set-state-in-effect, immutability, and others) are not enabled, because turning them on surfaced roughly 20 real, legitimate findings -- components calling `Date.now()` during render, `setState` called synchronously inside an effect -- across pages built well before this pass, fixing which is a real follow-up refactor, not a lint-config change. See [docs/adr/0006-eslint-scope-and-ts7-compat.md](docs/adr/0006-eslint-scope-and-ts7-compat.md) for the full reasoning, including why `typescript` is pinned to 6.x rather than the 7.x line for tooling-compatibility reasons.

20. The Transport Knowledge Graph (roadmap feature 44) now has real ID-based relationships for its six sample corridors and about a dozen named agencies (`server/catalog.mjs`'s `agenciesForCorridor`/`operatorForCorridor`/`connectedCities`, and `stations` as a real entity) -- not yet the roadmap's full entity list (Route/Trip/Vehicle/Stop/Platform/Fare/Connection as distinct graph nodes), and not a persisted graph store (it's still an in-memory catalog module, just with real relationships instead of name matching within it). The other ~50 seeded agencies with no sample corridor still resolve only through the original name-substring fallback. `tests/catalog.test.mjs` (14 tests) covers the new relationships and the fallback paths.

21. A real regional GTFS data pilot (this session's own plan's stretch goal, contingent on network reachability) was attempted and found genuinely blocked in this environment, not merely inconvenient: `curl` to MBTA's own GTFS static feed CDN and its live API host both returned a `403` from this environment's network egress proxy (`Received HTTP code 403 from proxy after CONNECT`), the same allowlist behavior already documented elsewhere in this checkpoint for the Chromium binary download attempted for accessibility testing (item 18). `registry.npmjs.org` and `github.com` remain reachable -- the allowlist is real and scoped, not a general outage -- but no public transit data host tried was on it. This means even the reduced "static-schedule ingestion only" fallback the stretch goal allowed for isn't reachable here; a real GTFS pilot needs either a broader network allowlist for this environment or a different execution environment entirely, on top of the hosting/ownership decisions already flagged as the user's to make (see the "What's blocked" triage this session's plan opened with).

22. A real local-LLM upgrade to the Agent feature (roadmap feature 46) was built and is fully tested (`tests/agent.test.mjs`, 26 tests, all against an injected mock model or a mocked `fetch` -- no live model or network dependency in the automated suite), and ships with the model disabled by default: `OLLAMA_BASE_URL`/`OLLAMA_MODEL` are unset unless you configure a real, separately-run Ollama instance yourself, because this environment cannot host one persistently on its own. `server/domain/agentGraph.mjs` orchestrates the flow with LangGraph (`@langchain/langgraph`, open-source, no account needed); the model classifies intent and may rephrase the reply's tone, but is never the source of a fact -- it can only reword what the existing deterministic, journey-grounded logic already produced, and a guard (`isSuspectRewrite`) rejects any rewrite that drops a number the original carried. Optional LangSmith tracing (`langsmith`, requires the user's own account) is a true no-op -- same function reference, zero network calls -- unless `LANGSMITH_TRACING`/`LANGSMITH_API_KEY` are both set.

    This was then genuinely validated against a real pulled model, not left as an assumption. First, in this environment's own constrained sandbox (no swap, 3.8 GB RAM, no GPU): a real user-pulled `llama3.2` 3B was pointed to via Ollama's own `OLLAMA_MODELS` variable, which surfaced and fixed two real bugs -- an Ollama-version-incompatible `format: <schema object>` request (fixed by sending `format: "json"` plus a textual schema description, now covered by a mocked-`fetch` test) and a default context window too large for that constrained hardware (fixed by an optional `OLLAMA_NUM_CTX`/`OLLAMA_TIMEOUT_MS` pair of env vars, unset by default) -- and confirmed individual real classify/compose HTTP round-trips succeeded, though the sandbox's measured ~0.5-1.5s/token throughput prevented running the full three-case `scripts/llm-smoke-test.mjs` sequence back-to-back in one sitting there. Second, and more conclusively, the user then ran that same unmodified script on their own real machine end to end: every request completed in 4-17 seconds (no sandbox throttling), and of three test questions, one got a genuine model-classified, model-composed reply while the other two correctly fell back to the deterministic regex classifier because the model's answer didn't land on a fixed intent -- a measured 1-of-3 real-world classify hit rate for `llama3.2` 3B on this prompt, which is a model-capability limit, not a code defect (the fixed `intents` list is still checked in JS regardless of what the model says, so a miss can only ever fail safe). In direct response to that measured hit rate, `classifyIntent` was then tuned (natural-language hints per intent, three few-shot examples, and tolerance for a model that wraps its JSON in markdown fences or extra prose) to give a small local model a better real chance, without touching the safety check itself -- see docs/adr/0008-real-llm-agent.md for the full account, including that this specific tuning change has not yet been re-validated against the real model that motivated it.

    This was validated against a real local model, not left as an untested code path: the user pulled a real `llama3.2` (3B, Q4_K_M, ~2 GB) with their own `ollama pull llama3.2`, and it was pointed at from this environment's own Ollama binary (installed the same way documented in [docs/adr/0008-real-llm-agent.md](docs/adr/0008-real-llm-agent.md)) via Ollama's own `OLLAMA_MODELS` variable, so no second copy of the model was downloaded. That surfaced two real bugs/gaps, both now fixed and covered by a test against a mocked `fetch`, not just described: `OllamaChatProvider` was sending `format: <schema object>` for the classify step (Ollama's newer structured-outputs feature), which 400s outright against this real install's Ollama version (0.3.14) with `"json: cannot unmarshal object into Go struct field ChatRequest.format of type string"` -- fixed by sending the broadly-supported `format: "json"` string plus the schema described as plain text instead, which doesn't weaken the safety property (`classifyIntent` re-checks the answer against the closed `intents` list in JS regardless of which format mode produced it); and the machine this Ollama install ran on (3.8 GB RAM, no GPU, no swap) could not load the model at its default context size at all (`"model requires more system memory than is available"`) until context was capped, which is why `OLLAMA_NUM_CTX` exists as a real, validated env var now, not a hypothetical one.

    On that same machine, real HTTP requests through this exact code path -- both the classify step's new JSON encoding and the compose step's free-form rephrasing -- each independently returned correct, genuinely model-generated output (a correct `{"intent":"cost"}` for a cost question; a real reworded version of a grounded reply for a boarding question, labeled `· composed` in the response). What did not fit in one sitting was running all three cases of `scripts/llm-smoke-test.mjs` back-to-back on that specific machine: prompt processing there measured on the order of half a second to a second and a half per token (a CPU/throttling limit of that one sandboxed environment, not of the code), which is also why `OLLAMA_TIMEOUT_MS` exists as a second real, validated env var -- raise it on a slow host rather than have a real, working request abort as "unavailable." `scripts/llm-smoke-test.mjs` now also accepts `MODEL_NAME` (use a model you've already `ollama pull`'d, the common case) as an alternative to its original raw-`.gguf`-file-plus-generated-`Modelfile` path, and `OLLAMA_MODELS` to point at an existing Ollama install's models directory instead of pulling a second copy. On typical, unconstrained hardware the full three-case script should complete in well under a minute.
