# Working in this repository (humans and AI agents)

Codex, Cursor and GitHub Copilot's coding agent read this file automatically, and Claude Code
reads it through `CLAUDE.md`. If your tool uses a different instruction file, point it here.
If you are an AI agent, treat everything below as binding instructions for this repository.

## The two files that matter

- **`HANDOFF.md` is the shared memory of sessions.** It says where the last session
  stopped, the repository state, the current focus, known limits, decisions and an
  append-only session log.
- **`ROADMAP.md` is the shared goal tree.** Long-term goals (`G1`) contain sub-goals
  (`G1.1`) with a horizon (`short-term`, `mid-term`, `long-term`), a priority (`P0` to
  `P3`) and a status, and each sub-goal contains tasks (`G1.1.1`). Its summary block is
  generated by `scripts/roadmap.py`.

Every agent or person who changes anything in this repository must read both before
starting and update them before finishing. Chat history is lost between sessions and
between tools; these files are not.

### At the start of a session

1. Read `HANDOFF.md` section 1 ("Last step") in full. It tells you exactly where the
   previous session stopped, what state it left the tree in, and how to resume.
2. Skim `HANDOFF.md` sections 4 (current focus) and 6 (known limits) so you do not
   re-discover known problems or redo finished work.
3. Run `python scripts/roadmap.py next` to see actionable roadmap work and the decisions
   waiting on the user. Do what the user asked; when the user gave no specific task, take
   the highest item from `next` or from section 4.
4. Run `git status --short` and compare it with `HANDOFF.md` section 2. If they disagree,
   trust git and record the discrepancy in your session-log entry.

### Before you finish (every time, even for small changes)

1. Update `ROADMAP.md`: check finished tasks with a `(done YYYY-MM-DD: evidence)` note,
   set sub-goal statuses, and add any newly discovered work as tasks or sub-goals.
   Follow the rules in its "How this file works" section.
2. Regenerate the roadmap summary with `python scripts/roadmap.py write`.
3. Update `HANDOFF.md` section 1 ("Last step") so it describes *your* session: what
   happened, what state the tree is in, and the exact steps the next agent should run first.
4. Update `HANDOFF.md` sections 2 to 7 wherever your work changed the facts. Section 4
   lists the current focus by roadmap ID; every ID there must still be open.
5. Add a new entry at the **top** of `HANDOFF.md` section 8 using the template there.
   Newest entry first. Never edit or delete older entries; they are the audit trail.
6. Run `python scripts/check_handoff.py --strict` and fix anything it reports. It checks
   `HANDOFF.md`, `ROADMAP.md` and every roadmap ID that `HANDOFF.md` mentions, and it
   fails if code changed but `HANDOFF.md` did not.
7. If you commit, include `HANDOFF.md` and `ROADMAP.md` in the same commit as the code
   they describe.

### How to write a good handoff

- **Facts, not intentions.** "Ran the full test suite: 212 passed" is useful.
  "Tests should pass" is not. If you did not run something, say you did not run it.
- **Be honest about what is broken or unverified.** The next agent will find out anyway;
  finding out from you is cheaper. Say how strongly something was verified.
- **Point at files, commands and roadmap IDs**, not descriptions.
- **Explain the why** for anything a future agent might be tempted to undo.
- **Keep it current, not complete.** `HANDOFF.md` section 3 is a ledger, not a changelog;
  git history holds the details. When the session log exceeds about 30 entries, move the
  oldest ones to `docs/handoff-archive/<year>.md` and link it.

### How to change the roadmap

- Never renumber, reuse or delete IDs. Set `dropped` with a reason instead.
- A sub-goal needs a metadata line, a `Done when:` line, and ideally `Why:` and `Evidence:`.
- Only the user resolves `decision` sub-goals. Ask, then record the answer in
  `HANDOFF.md` section 7 and move the sub-goal forward.
- Ideas without a committed outcome go in "Ideas not yet goals". Rejected suggestions go
  in "Considered and not adopted" with the reason.

## Engineering conventions that must hold

- **React in `src/` is the only UI source.** `standalone/` is regenerated by `npm run build`;
  never hand-edit it, or the next build silently discards the change.
- **Money is integer cents** with explicit currency. Floating-point amounts produce
  wrong totals and refunds.
- **No sample fallback on provider errors.** Show the failure, provenance and data age
  instead. A plausible fake route or price is worse than an honest outage.
- **The model is never the source of a fact.** Prices, statuses and conditions come from
  structured provider evidence; application code validates every model-chosen action, and
  protected traveler and card inputs are never sent to the model.
- **Provider gates stay closed without provider approval.** Fixture tests do not authorize
  live transactions (`docs/PROVIDER_READINESS.md`).
- **Every mutation is CSRF-protected, owner-scoped and versioned.** Updates carry the current
  version and return 409 on conflict; saving requires an idempotency key.
- **Auth responses stay enumeration-resistant, and tokens never reach logs.** See the R09
  notes in `server/email.mjs`.
- **TypeScript stays on 6.x** until tooling supports 7.x (`docs/adr/0006-eslint-scope-and-ts7-compat.md`).
- **No invented evidence.** Documents report measured results only. If you change
  behaviour that a report covers, re-run it or state in `HANDOFF.md` that it is stale.
- **Line endings.** Do not reformat whole files just to change line endings; it hides real diffs.

## Things not to do without asking the user

- Commit or push. Leave changes in the working tree and describe them in `HANDOFF.md`
  unless the user asked for a commit.
- Delete or rewrite session-log history in `HANDOFF.md`.
- Renumber or delete roadmap entries, or resolve a `decision` sub-goal on the user's behalf.
- Change measured numbers in any evidence or validation document without a new run.
- Add credentials, secrets or local data files to git.
- Set any provider approval or live flag (`DUFFEL_*`, `FLIGHTAWARE_*`) to true.
